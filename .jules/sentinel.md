## 2026-02-24 - [Metadata Injection Prevention]
**Vulnerability:** User-controlled data (filenames, codecs) containing control characters or excessive length can be written to EXIF tags, potentially causing metadata corruption or parser issues.
**Learning:** `ExifInterface` does not automatically sanitize or truncate strings. Filenames from `VideoMetadata` are user-controlled and can contain garbage.
**Prevention:** Sanitize all string inputs to EXIF tags by removing control characters (including newlines) and enforcing a reasonable length limit before writing.
## 2026-03-24 - [PII Leakage in Logs]
**Vulnerability:** Full stack traces containing PII (like absolute file paths, URIs, or MediaStore data) are leaked into system logs on production builds when exceptions occur during frame extraction or export.
**Learning:** `android.util.Log` calls in core library modules unconditionally dump stack traces regardless of the application's debuggable state.
**Prevention:** Use a centralized `LogUtils` wrapper that checks `ApplicationInfo.FLAG_DEBUGGABLE` via a `Context` parameter. In release builds, log only the exception's class name to prevent sensitive data exposure.
## 2026-04-28 - [Implicit Intent Hijacking]
**Vulnerability:** Launching an implicit `ACTION_VIEW` intent with sensitive content (like exported file URIs) without user interaction can lead to intent hijacking. A malicious app can register as the default handler and silently intercept the URI and data.
**Learning:** `Intent.ACTION_VIEW` relies on the Android system to resolve the appropriate application. If a default app is already set, or if a malicious app claims to handle the intent, sensitive data might be leaked.
**Prevention:** Wrap implicit intents for sensitive actions (like opening files or sharing) in `Intent.createChooser()`. This forces the system to display an app selection dialog, requiring explicit user action to choose the handling application.
## 2026-05-18 - [Filename Sanitization Bypass]
**Vulnerability:** A malicious filename containing control characters, multiple dots, or hidden leading/trailing periods could bypass simple string sanitization like `replace("..", "_")` and potentially cause path traversal, hidden files or errors when saved via `MediaStore`.
**Learning:** Simple string replacement is insufficient for robust filename sanitization. `replace("..", "_")` fails if the input is `...`. The default `trim()` only removes whitespace but leaves dots or underscores.
**Prevention:** Filename sanitization must explicitly strip control characters (hex 0x00-0x1F, 0x7F) and illegal filesystem characters (`\/:*?"<>|`). To prevent path traversal, collapse multiple consecutive dots (e.g., using `Regex("\\.\\.+")`) into a single underscore. To avoid hidden files or malformed boundaries, trim leading and trailing dots, underscores, and whitespace from the resulting name (e.g., `.trim { it == '_' || it == '.' || it.isWhitespace() }`).
## 2025-02-23 - Prevent temporary file leakage on export failure
**Vulnerability:** The video clipping process (`extractVideoClipOnce` in `FrameExporter`) creates a temporary MP4 file but could exit prematurely (e.g., via exception during muxing or extraction). Without an explicit cleanup mechanism triggered by an error state, this could leak temporary files in the app's cache directory, potentially leading to storage exhaustion (a localized Denial of Service).
**Learning:** While some temp file creations in the class correctly used `try...finally { tempFile.delete() }` (e.g., `writeExifToJpegBytes`), complex multi-stage extraction functions failed to guarantee cleanup of the main output file upon an early exit or exception.
**Prevention:** When orchestrating complex media processes that create temporary files, wrap the core logic in a `try...finally` block. Use a `success` boolean flag set to `true` exactly before the return statement, and verify `if (!success) file.delete()` within the `finally` block to guarantee safe cleanup of incomplete or orphaned media artifacts.
## 2026-06-25 - [MediaFormat API Compatibility and DoS Mitigation]
**Vulnerability:** Invoking `MediaFormat.containsKey()` (which requires API 29+) on older Android devices (API 26-28) throws a `NoSuchMethodError`. When parsing untrusted or maliciously crafted media files that lack expected format keys, this uncaught linkage error immediately crashes the application, presenting a local Denial of Service (DoS) vulnerability.
**Learning:** Standard lint rules or IDE warnings might not always catch API-level violations on specific system framework classes. Broad find-and-replace strategies to fix these issues can be dangerous if they accidentally modify identically named methods on unrelated standard collections (like `Map.containsKey`).
**Prevention:** Replace all `MediaFormat.containsKey()` checks with safe retrieval attempts wrapped in `runCatching` blocks (e.g., `runCatching { format.getInteger(key) }.getOrNull()`). Ensure modifications are strictly scoped to the `MediaFormat` class context and validated against regression on cache/state collections.
